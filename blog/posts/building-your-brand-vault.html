01 / THE STRUCTURE

The vault structure

Resist the urge to start complex. I've seen teams build elaborate taxonomies before writing a single file, and the whole thing collapses under its own weight. The structure I use is five folders. That's it. You can add depth later, but you cannot easily remove it.

your-brand/
├── CLAUDE.md          # Agent orientation — read this first
├── concepts/          # Atomic brand facts (one per file)
├── rules/             # Brand guidelines as actionable statements
├── playbooks/         # Campaign narratives and messaging frameworks
├── proof/             # Case studies, data, testimonials
└── voice/             # Real examples of your brand done right
The five-folder vault — simple enough to maintain, structured enough for an agent to navigate

Each folder serves a specific function in the knowledge pipeline. They're not arbitrary categories — they map to the progression from atomic facts to executable agent capabilities.

02 / THE FIVE FILE TYPES

The five file types — and what belongs in each

1. Concepts — the atomic layer

One idea per file. The discipline here is ruthless specificity. "Brand positioning" is one file. "Target audience" is one file. "Product pricing philosophy" is one file. If a file is trying to answer more than one question, split it.

The template:

---
tags: [concept]
description: "One sentence explaining precisely what this file contains"
---

**[concept-name]** — Your one-line definition goes here. This is what
the agent reads if it doesn't need more depth.

## What this means in practice

[Two to four paragraphs of explanation. The specific version, not the
generic one. What does this mean *for your company*, not in the abstract.]

## What it isn't

[Optional but valuable. Common confusions, things people mistake this for.]

## Related

[[related-concept]] | [[another-concept]]

The description field in the frontmatter is the most important line in the file. It's what the agent reads when scanning the vault — it decides whether to open the file based on this alone. Bad descriptions waste agent context. Good descriptions are specific enough to make the relevance decision obvious.

Bad descriptionGood description
"Brand stuff""Core brand voice characteristics — technical authority with practical warmth, no corporate jargon"
"Our product""Primary product positioning — why we lead with reliability over cost for infrastructure buyers"
"Marketing""Campaign narrative for enterprise vertical — audience, key messages, channel strategy"

2. Rules — the guideline layer

Rules are the "always/never" statements distilled from your concepts. They're the things that should never be violated in any content your team or your AI produces. Keep them short, specific, and linked to the concepts they derive from.

---
tags: [rule]
description: "When writing for enterprise buyers, open with reliability
metrics before product features"
---

**Lead with reliability for enterprise audiences.**

Enterprise infrastructure buyers care about uptime before they care about
features. Every piece of content targeting this segment should anchor in
reliability data, SLAs, or uptime case studies within the first two
paragraphs.

## Why this works

[The reasoning. Brief. Helps the agent (and humans) understand when to
apply this and why it matters.]

## Applies to

[[enterprise-positioning]] | [[campaign-narrative-enterprise]]

## Source

Derived from [[target-audience]] and [[brand-positioning]].

Name rule files as statements, not topics. lead-with-reliability.md not reliability-rule.md. The filename becomes the link text in Obsidian, and a statement is more useful than a label.

3. Playbooks — the strategy layer

Playbooks are where concepts and rules combine into operational strategy. Your existing campaign documents, messaging frameworks, and channel guides become playbooks — restructured for navigability rather than presentation.

---
tags: [playbook]
description: "Enterprise campaign narrative — audience profile, messaging
arc, key messages by channel"
---

## Audience

[Specific description of who this is for. Role, industry, pain points,
decision-making context. Reference [[target-audience]] for the full profile.]

## Narrative arc

1. **The problem**: [Their actual pain, stated in their language]
2. **The cost**: [What it's costing them — quantified where possible]
3. **The shift**: [What changes when they have your solution]
4. **Your role**: [Your positioning — reference [[brand-positioning]]]
5. **Proof**: [The evidence — link to [[proof/case-study-enterprise]]]

## Key messages

- Primary: "[One-sentence value proposition]"
- Supporting: "[Specific proof point]"
- Supporting: "[Differentiator]"

## By channel

| Channel  | Hook style          | CTA                    |
|----------|---------------------|------------------------|
| LinkedIn | Insight/data lead   | "See how [client] did it" |
| Website  | Problem-solution    | "Talk to our team"     |
| Email    | Case study lead     | "Get the full report"  |

## Voice

Follow [[brand-voice]]. Apply [[lead-with-reliability]].
Reference [[voice/exemplar-enterprise-linkedin]] for tone.

4. Proof — the evidence layer

Every claim needs backing. The proof folder is where that backing lives — structured consistently so the agent can pull specific data points when it needs them.

---
tags: [proof, case-study]
description: "Enterprise client case study — deployment scale, performance
metrics, 3-month ROI data"
---

## Client

[Company or anonymised reference]

## Challenge

[Their situation before. Specific pain points, scale, constraints.]

## Solution

[What you did. How it was structured. What made it different.]

## Results

- [Metric]: [X]% improvement over [time period]
- [Metric]: [X] vs previous approach
- [Metric]: [X] weeks for [X] deliverables

## Quotable

"[Direct quote from client contact]"
— [Name], [Title], [Company]

## Referenced by

[[campaign-narrative-enterprise]] | [[lead-with-reliability]]

5. Voice exemplars — the tone reference layer

These are real examples of your brand voice done well. They're the reference standard for both humans writing copy and agents generating content. Don't overthink these — paste in your five best LinkedIn posts or emails, add a few sentences about why they work, and you're done.

---
tags: [voice, exemplar]
description: "LinkedIn post example — insight-led, data-grounded,
conversational without being casual"
---

## The post

[Paste the actual content here, exactly as published]

## Why this works

- Opens with a contrarian observation, not a product mention
- Specific number in first two lines (anchors authority)
- No hard sell — the expertise IS the sell
- Follows [[brand-voice]] and [[lead-with-reliability]]

## Context

Posted [date]. [X] impressions, [X] engagements.
03 / THE CLAUDE.MD FILE

The CLAUDE.md file — your most important document

This is the file that makes the vault agent-ready. When Claude Code opens a session in your vault folder, it reads CLAUDE.md automatically. Without it, the agent treats the vault as a generic folder. With it, the agent understands what it's looking at and how to work with it.

Keep it short. One page. Here's the template I use:

# [Company] Brand Vault

This vault contains [Company]'s brand positioning, messaging frameworks,
and voice guidelines. It is structured for both human browsing in Obsidian
and AI-assisted content generation via Claude Code.

## Structure

- `concepts/` — Atomic brand facts. One concept per file.
- `rules/` — Brand guidelines as actionable statements.
- `playbooks/` — Campaign narratives and messaging frameworks.
- `proof/` — Case studies, testimonials, performance data.
- `voice/` — Example content demonstrating brand voice done well.

## How to use this vault

1. Every file has a `description` in its frontmatter. Read descriptions
   before opening files to decide what's relevant.
2. Files link to each other with [[wikilinks]]. Follow links for context.
3. When generating content:
   - Start with the relevant playbook
   - Read `concepts/brand-voice.md` for tone
   - Reference at least one proof file for evidence
4. Never generate messaging that contradicts a rule file.
5. When uncertain about positioning, `concepts/brand-positioning.md`
   is the source of truth.

## Writing conventions

- Specific over vague. Numbers over qualifiers.
- Every claim must be supportable from a proof file.
- Lead with the reader's problem, not your solution.
- Technical accuracy is non-negotiable.

The key sections are: what the vault is, how it's structured, and the rules for using it. That's all the agent needs to orient itself and navigate correctly.

04 / THE LINKING DISCIPLINE

The linking discipline — why it matters more than the folder structure

The folder structure organises files. The links between files build the knowledge graph. The graph is what makes the system genuinely intelligent rather than just organised.

Here's the discipline:

  • Every concept links to related concepts. brand-voice.md links to messaging-pillars.md and tone-by-context.md.
  • Every rule links to the concepts it derives from and the playbooks it governs. lead-with-reliability.md links to brand-positioning.md (source) and campaign-narrative-enterprise.md (application).
  • Every playbook links to the rules it follows and the proof it references. campaign-narrative-enterprise.md links to lead-with-reliability.md, brand-voice.md, and proof/case-study-enterprise.md.
  • Every proof file links back to the playbooks and rules that reference it. case-study-enterprise.md links to campaign-narrative-enterprise.md.

This creates a graph where the agent can start anywhere and navigate to everything relevant. When you ask it to write an enterprise LinkedIn post, it doesn't need to read every file in the vault — it follows the links from the relevant playbook to exactly the context it needs.

How the graph looks in practice

An agent writing an enterprise case study will read: the relevant playbook → which links to brand-voice and lead-with-reliability → which links back to brand-positioning and the specific case study → which links to the testimonial and metrics. Five to eight files, all relevant, zero irrelevant noise. That's the graph working.

05 / BUILDING IT — THE HONEST TIMELINE

Building it — the honest timeline

I've now built this system from scratch with several clients. Here's what it actually takes:

StepWhat you're doingTime
SetupInstall Obsidian, create vault, set up five folders30 min
ConceptsWrite 8–12 core concept files from existing materials2–3 hours
RulesExtract 5–8 brand guidelines as rule files1–2 hours
PlaybooksRestructure 2–4 existing campaign docs as playbooks2–3 hours
ProofStructure 3–5 case studies or data files1–2 hours
VoiceAdd 5–8 exemplar content pieces with annotations1 hour
CLAUDE.md + testWrite orientation file, test with Claude Code, iterate1 hour
TotalHalf a day to a full day

After that initial build, maintenance is just writing. New product? New concept file. New campaign? New playbook. New case study? New proof file. The infrastructure never changes. No pipeline to re-run. No embeddings to regenerate. Edit the file, and the agent immediately sees the update.

The order matters

Start with concepts, not playbooks. The instinct is to migrate your big strategy documents first because they feel most important. Resist it. Those documents are synthesis — they depend on the atomic concepts being well-defined first. Write your ten core concept files, and you'll find the playbooks write themselves much faster because you have clear, linkable source material.

Test early, not at the end

After your first ten concept files and first rule file, run a test. Point Claude Code at the vault. Ask it to generate something simple — a LinkedIn post, a one-paragraph product description. See what it gets wrong. The gaps in the output tell you exactly what to write next. This is faster than trying to anticipate what the vault needs in advance.

06 / INTEGRATION PATTERNS

How to use it once it's built

Direct with Claude Code

The simplest pattern: open Claude Code in the vault directory. It reads CLAUDE.md automatically and has access to all files. Ask it to generate content, review drafts against brand guidelines, or check whether a piece of copy follows the rules. This covers 80% of use cases.

Skills for repeatable workflows

Once you find yourself running the same request repeatedly ("generate a LinkedIn post for this product announcement"), encode it as a skill — a SKILL.md file that gives the agent a precise workflow to follow every time. Skills reference the vault files they need and produce consistent outputs. This is how you get your AI to produce on-brand content without prompting it from scratch each time.

Team access

Store the vault on a shared drive — Google Drive, OneDrive, Dropbox. Team members open it in Obsidian for browsing and in Claude Code for AI-assisted generation. Everyone works from the same source of truth. When someone updates a rule file, everyone's agent sessions immediately reflect it. No sync required.

The upgrade path is always open

If the vault grows beyond 200+ files and navigation starts to feel slow, the structured markdown files you've built are perfectly valid input for an embedding pipeline. You can add vector search without throwing away any of the work you've done. Starting with structured files keeps all options open. Starting with a RAG pipeline gives you one option from day one.
