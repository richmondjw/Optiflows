Your AI Needs a Filing System, Not a Database

Why structured markdown beats vector search for most companies
OptiFlows — April 2026
The short version: Most companies reach for a vector database when they want AI to use their knowledge. That is almost always the wrong tool. For teams with fewer than a few hundred documents, a well-structured folder of markdown files — what I call an agentic PKM — gives you better results, in an afternoon, with zero infrastructure. The vault is the database. The structure is the retrieval system.
01 / THE REAL PROBLEM

The real problem isn't retrieval — it's organisation

I've worked with dozens of marketing teams who all share the same pain: their brand knowledge is scattered. Strategy decks in Google Drive. Campaign briefs in Notion. Website copy in a CMS. Sales messaging in someone's head. When they finally sit down to use an AI tool, they paste in whatever they can find from memory and hope for the best.

The conventional fix is RAG — retrieval-augmented generation. Chunk your documents, push them through an embedding model, store the vectors in a database, wire up a retrieval API, and query by similarity at runtime. It's a real solution to a real problem. But it's a lot of infrastructure for a problem that usually has a simpler answer.

The simpler answer: AI agents don't need vector search to find relevant content. They need well-organised files. An agent can read a folder. It can follow a link. It can scan a one-line description and decide whether to open a file. If your knowledge is structured well, navigation replaces retrieval — and you get to skip the entire pipeline.

02 / WHAT AN AGENTIC PKM ACTUALLY IS

What an agentic PKM actually is

PKM stands for personal knowledge management. The idea has been around for decades — a structured system for capturing and connecting what you know, so you can find and use it later. Tools like Obsidian have made it practical for individuals. What's new is applying the same architecture to company knowledge, and making it traversable by an AI agent, not just a human.

An agentic PKM is a vault — a folder of markdown files — where knowledge is structured to serve two users equally: the human who writes in it, and the AI that navigates it. Both traverse the same files. The structure that makes it easy for a human to browse is the same structure that makes it easy for an agent to reason.

The pipeline that makes it work looks like this:

concept  -->  rule  -->  playbook  -->  skill
 (atom)       (guideline)  (strategy)   (capability)
Knowledge matures from atomic facts to executable agent capabilities

Each layer has a purpose:

  • Concepts are atomic. One idea per file. "What is our positioning?" One file. "Who is our primary buyer?" One file. Each stands alone and links to related concepts.
  • Rules are the distilled guidelines — the "always" and "never" statements that keep everything consistent. "Lead with outcomes, not features." "Never use jargon without explaining it in the same sentence."
  • Playbooks weave concepts and rules into coherent strategy for a specific context. A messaging framework. A campaign narrative. A channel guide. These are the documents your team already has — just restructured for navigability.
  • Skills are the agentic layer. Instructions that tell the AI exactly what to do, what files to read, and in what order to produce a specific output.
03 / HOW AN AGENT ACTUALLY NAVIGATES IT

How an agent navigates — and why structure replaces search

This is where it gets concrete. When I point Claude Code at a well-structured vault and ask it to write a LinkedIn post for a product launch, here's what actually happens:

  1. It reads the CLAUDE.md file at the root — a short orientation that explains what the vault contains and how it's organised.
  2. It finds the relevant skill file — in this case, something like skills/write-linkedin-post.md — which tells it exactly which files to read and what to produce.
  3. It follows the links in that skill to the relevant concept files (brand voice, product positioning), rule files (tone guidelines), and proof files (relevant case studies).
  4. It generates output that is grounded in the actual knowledge — not a hallucinated approximation of it.

No vector search. No similarity scores. No over-retrieval of tangentially related chunks. The agent navigates the same way a thoughtful human would — by reading what's relevant and following the links to what else matters.

The key insight: frontmatter as a scan layer

Every file in the vault has a YAML frontmatter block with a one-line description. The agent can scan fifty file descriptions in seconds and decide which three to actually open. It's progressive disclosure — most retrieval decisions happen before reading a single full file. This is faster and more precise than vector similarity at the scale most companies operate at.

The knowledge graph that emerges from consistent linking is also genuinely useful. Every concept links to related concepts. Every rule links to the concepts it derives from and the playbooks it governs. Every playbook links to the rules it follows and the evidence it references. The agent can start anywhere and navigate to everything relevant. No retrieval pipeline needed.

04 / WHEN THIS BEATS RAG — AND WHEN IT DOESN'T

When this beats RAG — and when it doesn't

I'm not arguing against vector databases categorically. They're excellent at scale. If you have tens of thousands of documents, no human could maintain a link structure across them, and vector similarity becomes the only practical retrieval mechanism.

But most companies aren't at that scale. Most companies have 20 to 150 core knowledge documents. At that scale, a structured file system with good links consistently outperforms embeddings — because the structure encodes meaning, not just co-occurrence. A link from a rule file to a case study means something specific. A vector similarity score between the same two chunks is a statistical approximation of that relationship.

FactorVector DB (RAG)Agentic PKM
Setup timeDays to weeks — ingestion pipeline, schema, embedding modelAn afternoon — create vault, write files
Content updatesEdit file → re-ingest → regenerate embeddingsEdit file. The agent sees it immediately.
Retrieval qualityDepends on chunk size and embedding model choicesDepends on file structure and link quality
Maintenance overheadPipeline monitoring, model versioning, database opsNone. Write files. Link them.
CostDatabase hosting, embedding API calls at query timeZero beyond Claude Code access
Human usabilityRequires a query interface to browseObsidian — graph view, backlinks, search
Upgrade pathLocked in from day oneThe same files feed a RAG pipeline later if needed

That last row matters. Starting with structured markdown doesn't close off the RAG option — it keeps it open. Your files are perfectly valid input for an embedding pipeline if you ever need one. Starting with the pipeline, on the other hand, commits you to infrastructure from day one and gives you nothing useful for human browsing.

05 / HOW I BUILT THIS AT OPTIFLOWS

How I built this at OptiFlows — and what it taught me

OptiFlows itself runs on an agentic PKM. The vault I built to run my own consulting practice is the same architecture I install for clients. I built the initial version in a single extended session — around twelve hours — and it's been the backbone of everything since.

A few things I learned that aren't obvious from the outside:

The CLAUDE.md file does more work than you'd expect. This is the orientation document at the root of the vault. When Claude Code opens a session in the vault folder, it reads this file first. A good CLAUDE.md doesn't just describe the structure — it tells the agent what the vault is for, what conventions to follow, and what to do when it's uncertain. Think of it as the onboarding document for your AI team member.

The one-line description on every file is non-negotiable. I skipped this early on and immediately felt the cost — the agent was opening files unnecessarily, losing context, and occasionally hallucinating about what a file contained before reading it. A good description lets the agent make confident decisions without opening the file. This is the single highest-leverage structural habit in the whole system.

Start with ten files, not fifty. The instinct is to migrate everything at once. Resist it. Write ten core concept files — your positioning, your voice, your primary audience, your top three rules — and test the agent against them. You'll learn more from ten well-structured files than from fifty hastily converted ones. Build the link structure as you go. The graph gets smarter over time.

06 / WHERE TO START

Where to start

If this resonates, here's the minimal path to a working system:

  1. Install Obsidian. Free. Mac, Windows, Linux. Stores everything as local markdown files that you own and control.
  2. Create your vault. A single folder. Name it after your company or project.
  3. Write your ten core concept files. Brand positioning. Voice and tone. Primary audience. Top messaging pillars. These are the atomic facts your AI needs to work from.
  4. Add your rules. Three to eight "always/never" guidelines. Keep them short, specific, and linkable.
  5. Write a CLAUDE.md. One page. Explain what the vault is, how it's structured, and what the agent should do with it.
  6. Point Claude Code at the folder. Ask it to generate something. See what it gets right and wrong. The gaps in the output tell you exactly what to add to the vault next.
